## Anti-patterns verdict

The concept is polished and does not require a visual redesign. It does lean toward a familiar dark productivity-console pattern, but the Fraunces headings, household language, yellow time vocabulary, and practical task density give it a distinct HomeOps character.

The deterministic detector found one advisory in `apps/web/src/index.css:220`: a literal `24px` font size outside the documented ramp. It found nothing representative in the Today route because that route is still a placeholder. Browser accessibility inspection was skipped because it would test the placeholder rather than the concept.

## Overall impression

The layout is viable. Its biggest opportunity is to make the visual urgency order, DOM order, keyboard order, and mobile order tell the same story. Most concerns are implementation constraints rather than reasons to alter the desktop composition.

## What's working

- External Today and Due soon headings create a warm, readable hierarchy without turning every region into an identical card.
- Plain task names, visible dates, category context, and blocker explanations make the page quickly understandable.
- The yellow time language, green completion action, and red blocked signal form a coherent semantic palette when reinforced with text and icons.

## Priority issues

### [P1] Reading order and responsive collapse

The two-column layout creates two simultaneous scan paths. Desktop visual order, DOM order, and phone order must agree. Use the phone sequence Today, Blocked, Due soon, Coming up. At narrow widths and 200–400% zoom, rows must reflow without horizontal scrolling; title and due state take priority over category, owner, and secondary actions.

### [P1] Task-row interaction semantics

Do not implement a clickable row as a link containing the completion control and overflow button. Use a semantic list row with sibling controls: a labelled completion button or checkbox, a task-title link, and a separately labelled menu button. Each needs visible focus and predictable keyboard order.

### [P1] Completion feedback and recovery

The completed row is a useful visual state, but the interaction also needs pending feedback, stable focus, a screen-reader status announcement, Undo, and rollback on failure. Do not rely on green or strikethrough alone.

### [P1] Blocked and ownership semantics

A blocked task must not look directly completable; use a distinct blocked indicator and expose its next valid action. Portraits alone are not sufficient ownership information. Provide visible names where space allows and an accessible name such as “Assigned to Maya” everywhere.

### [P2] Duplicate actions and compact controls

The page-level Add task and two inline Add task actions create extra tab stops and unclear differences. If all open the same workflow, retain one primary action. If inline actions prefill different due states, label them “Add task due today” and “Add task due soon.” Completion, overflow, bell, and disclosure controls should have at least 44×44 CSS-pixel hit areas even when their visible glyphs stay smaller.

### [P2] Contrast-sensitive secondary UI

Current dark tokens provide good contrast for normal muted, secondary, mint, and ochre text. Risks remain if opacity is reduced: disabled text is approximately 3.63:1 on the dark canvas, the default border is below 2:1, and small mint text on mint wash has little tolerance. Necessary boundaries need a 3:1 non-text contrast treatment; normal text needs 4.5:1.

## Persona red flags

**Accessibility-dependent keyboard or screen-reader user:** needs named completion/menu controls, one `h1` plus logical `h2` sections, a skip link, visible focus, status announcements, and DOM order matching the visual order. The duplicate visible “Today” can remain if the section receives a more descriptive accessible label such as “Tasks due today.”

**Distracted mobile user:** the desktop row contains too many horizontal fields, compact controls invite missed taps, and the primary Add task button is outside the thumb zone. The mobile composition should preserve title, completion, and due timing first, while moving category, owner, and secondary actions below or behind disclosure.

**Ordinary household member:** avatar-only assignment, ambiguous section counts, and identical Add task labels require interpretation. Counts should mean remaining actionable items; owner names and scoped Add task labels should be explicit.

## Minor observations

- Keep a completed item briefly, then move it behind a “1 completed” disclosure or remove it after confirmation.
- Label every overflow control with its task name.
- Treat task groups as lists and dates as semantic `time` elements.
- The notification control should announce the unread count.
- Test empty, loading, partial-error, long-title, localization, large-household, and 20+ task states.
- The current shell has no skip-to-main link.

## Questions to consider

- If the user opens Today for twenty seconds, what identifies the first task worth acting on?
- Do the inline Add task rows create meaningfully different tasks, or only repeat the primary action?
- Should ownership remain compact and portrait-led, or become explicit text in the comfortable-density view?
